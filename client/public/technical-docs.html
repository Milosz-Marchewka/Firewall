Technical Documentation

Introduction

Project Overview

Firewall is a browser-based, turn-based multiplayer game with a React (Vite) frontend and a Node.js/Express backend. Persistent data is stored in MongoDB, and real-time gameplay state is synchronized using Socket.IO.

This document focuses on implementation details: repository layout, runtime data flow, API routes, WebSocket events, and how the server resolves abilities and turns.

Tech Stack

  • Client: React + Vite + TailwindCSS
  • Server: Node.js + Express
  • Realtime: Socket.IO
  • Database: MongoDB via Mongoose
  • Auth: JWT stored in an httpOnly cookie

Repository Structure

The project is split into two main folders:

  • client/ — React UI, assets, and the Socket.IO client binding
  • server/ — Express routes/controllers, Socket.IO server, and Mongoose models

Important entry points include client/src/main.jsx (client bootstrap), client/src/App.jsx (routing), and server/index.js (Express + Socket.IO server startup).

Requirements

Runtime (Players)

  • A modern web browser
  • An active internet connection
  • A screen resolution of 1920×1080 (recommended)

Development (Local Setup)

  • Node.js + npm (LTS recommended)
  • A running MongoDB instance
  • Ports 5173 (client) and 5000 (server) available

Environment Variables

The backend reads environment variables using dotenv and expects at minimum:

  • URI — MongoDB connection string (used by server/src/db/Connection.js)
  • JWT_SECRET — secret used to sign/verify auth tokens

Optional variables include URL_BASE (used when generating room URLs) and NODE_ENV (affects cookie secure settings).

Local Development

Local Development (Recommended)

The client talks to the server through REST (/api) and Socket.IO. During development, Vite proxies /api calls to http://localhost:5000.

  • 1) Start MongoDB
    Ensure MongoDB is running and you have a valid connection string.
  • 2) Start the server
    In server/: install dependencies, create a .env containing URI and JWT_SECRET, then run node index.js (or npx nodemon index.js for auto-reload). The server listens on 5000.
  • 3) Start the client
    In client/: run npm run dev. Vite starts on 5173.
  • 4) Open the app
    Navigate to http://localhost:5173.

Accounts (Guest vs Registered)

Authentication is cookie-based. Signup/login/guest endpoints set an auth cookie (JWT). The client checks the current session via GET /api/account/auth.

  • Guest: creates a Guest record and sets a short-lived JWT (24h).
  • Registered: creates a User record and sets a longer-lived JWT (7 days).

Frontend Architecture

Client Entry Points

The React app is bootstrapped in client/src/main.jsx and routed in client/src/App.jsx. Key routes include the lobby (/), entry/login (/hello), rooms (/room/:token), and documentation (/documentation).

REST Calls

The UI uses fetch calls against /api endpoints. In dev, these calls are proxied by Vite to the backend. Session validation uses credentials: "include" so the JWT cookie is sent.

Realtime UI Updates (Socket.IO)

The client creates a single shared Socket.IO instance in client/src/socket.js with autoConnect: false. Screens connect when needed and subscribe to events for room state, draft, and battle updates.

Server & Game Logic

Server Architecture

The backend is started from server/index.js. It mounts REST routes under /api and attaches Socket.IO (server/src/websocket/io.js) to the same HTTP server. Game state is stored in MongoDB in a Game document.

HTTP API (REST)

Game routes are defined in server/src/routes/GameRoutes.js and account routes in server/src/routes/AccountRoutes.js.

  • POST /api/play — create/find a room (quickplay or play)
  • POST /api/room and GET /api/room/:url — room creation/lookup
  • GET /api/abilities — list abilities (filtered by role)
  • POST /api/buyAbility — purchase/unlock an ability
  • GET /api/endData — end-screen summary data
  • POST /api/account/signup, /login, /guest, /logout
  • GET /api/account/auth — validate session (requires auth cookie)
  • POST /api/account/abilities — fetch owned abilities

WebSockets (Room → Draft → Battle)

The Socket.IO server is implemented in server/src/websocket/io.js. The main flow is:

  • join-room → server assigns the socket a role (attacker/defender) and a roomId
  • room-state + room-ready → broadcast lobby/room readiness
  • draft-* events → synchronize quickplay draft completion and picks
  • battle-* events → retrieve and update canonical battle state
  • leave-room / disconnect → release player slot and notify opponent

Ability Resolution

Abilities are persisted as metadata in the Ability collection and copied into the current Game document as a player’s battle deck (with an added currentCooldown field).

When the client emits battle-use, the server validates turn ownership and cooldown, applies the effect, updates the game log, advances the turn, ticks cooldowns, and emits a new battle-state.

  • damage — subtracts HP from the opponent (defender: integrity, attacker: persistence)
  • heal — restores HP; see “Healing Override” for overflow behavior
  • freeze — increments skipTurns for the opponent role

Healing Override

The server implements role-specific overflow behavior when a heal would exceed 20 HP:

  • Attacker: extra healing is converted into an overflow stat (reduced by half) that is added as a bonus to the next damage ability.
  • Defender: extra healing allows temporary HP above 20 (also reduced by half).

Persistence & Rewards

Player accounts are stored in MongoDB as either User (registered) or Guest. When a match ends, the server awards XP and skill points and updates level and levelPoints accordingly.
