Overview

The Cyber project is a real-time multiplayer game experience built with a React client and a Node.js server. Gameplay, matchmaking, and ability execution run on the server, while the client renders UI and syncs game state via REST endpoints and WebSockets.

The client folder contains UI, assets, and socket bindings. The server folder hosts API routes, DB models, and gameplay logic under controllers.

System Architecture

Client: React SPA communicates with the server via REST for setup/lookup and Socket.IO for live game updates.
Server: Express routes handle account/game endpoints. Socket.IO handles rooms, battle events, turn updates, and broadcasts.
Database: MongoDB stores users, guests, abilities, and persistent game state.

Runtime Data Flow

  1. Client initializes and establishes Socket.IO connection.
  2. Client uses REST endpoints to authenticate/initialize.
  3. Server assigns lobby/room and pushes state updates through WebSocket events.
  4. Client renders state; player actions are emitted as socket events.
  5. Server validates actions, applies ability effects, and persists state to MongoDB.

HTTP API

Primary route groups are defined in the server routes folder:

  • AccountRoutes — account creation, login, guest flow.
  • GameRoutes — game start, game state fetch, ability metadata.

API endpoints are defined under server/src/routes and route handlers live in server/src/controllers. Review the controller files for request/response schema.

WebSockets

Real-time functionality is provided by Socket.IO. The server defines WebSocket events in server/src/websocket/io.js. The client uses a dedicated socket module in client/src/socket.js.

Common Event Flow

  • connect → client joins the lobby.
  • room:join → server assigns a room.
  • game:state → server broadcasts canonical state.
  • action:cast → client submits an ability.
  • game:update → server publishes resolved effects.

Database

MongoDB collections are defined in server/src/db:

  • User — registered accounts and profile data.
  • Guest — ephemeral user profiles.
  • Game — game session state.
  • Abilities — ability definitions and metadata.

Auth & Sessions

Account logic is handled via AccountRoutes. Guest sessions are supported via the Guest model. The server should validate player ownership for any game action.

Game Logic

Gameplay and ability resolution live under server/src/controllers/abilities and server/src/controllers/room. Each ability handler validates preconditions, applies status changes, and queues broadcast updates.

Configuration

  • Client config is primarily in client/vite.config.js.
  • Server configuration lives in server/index.js and server/src/utils.js.
  • Database connection is defined in server/src/db/Connection.js.

Local Development

  1. Install dependencies in client and server folders.
  2. Start MongoDB locally.
  3. Run the server, then run the client.

The client runs on a Vite dev server and proxies requests to the API.

Deployment Notes

  • Build the client into static assets and host behind a CDN or static server.
  • Host the Node.js server separately with environment variables for DB and ports.
  • Ensure Socket.IO can connect across environments (CORS, HTTPS).

Testing & Diagnostics

  • Use server logs to trace ability resolution and room events.
  • Check browser console for socket connection issues.
  • MongoDB logs help track persistence and performance.

Security Notes

  • Validate all client input on the server.
  • Rate-limit account endpoints.
  • Restrict socket event payloads to known schemas.
  • Never expose secrets in client code.
