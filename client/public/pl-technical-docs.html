Dokumentacja techniczna

Wprowadzenie

Opis projektu

Firewall to przeglądarkowa, turowa gra wieloosobowa z frontendem w React (Vite) oraz backendem w Node.js/Express. Dane trwałe są przechowywane w MongoDB, a stan rozgrywki w czasie rzeczywistym jest synchronizowany przez Socket.IO.

Dokument opisuje szczegóły implementacyjne: strukturę repozytorium, przepływ danych w runtime, trasy API, zdarzenia WebSocket oraz sposób rozwiązywania tur i umiejętności po stronie serwera.

Technologie

  • Klient: React + Vite + TailwindCSS
  • Serwer: Node.js + Express
  • Realtime: Socket.IO
  • Baza danych: MongoDB + Mongoose
  • Autoryzacja: JWT w ciasteczku httpOnly

Struktura repozytorium

Projekt jest podzielony na dwa główne foldery:

  • client/ — interfejs w React, zasoby i klient Socket.IO
  • server/ — trasy/kontrolery Express, serwer Socket.IO i modele Mongoose

Kluczowe punkty wejścia to m.in. client/src/main.jsx (bootstrap klienta), client/src/App.jsx (routing) oraz server/index.js (uruchomienie Express + Socket.IO).

Wymagania

Uruchomienie (dla graczy)

  • Nowoczesna przeglądarka internetowa
  • Aktywne połączenie z internetem
  • Rozdzielczość 1920×1080 (zalecane)

Development (lokalnie)

  • Node.js + npm (zalecana wersja LTS)
  • Działająca instancja MongoDB
  • Wolne porty 5173 (client) i 5000 (server)

Zmienne środowiskowe

Backend wczytuje zmienne środowiskowe przez dotenv i wymaga przynajmniej:

  • URI — connection string do MongoDB (używane w server/src/db/Connection.js)
  • JWT_SECRET — sekret do podpisywania/weryfikacji tokenów

Dodatkowo można ustawić URL_BASE (generowanie linków do pokoju) oraz NODE_ENV (wpływa m.in. na flagę secure ciasteczek).

Uruchomienie lokalne

Uruchomienie lokalne (zalecane)

Klient komunikuje się z serwerem przez REST (/api) oraz Socket.IO. W trybie developerskim Vite przekierowuje wywołania /api do http://localhost:5000.

  • 1) Uruchom MongoDB
    Upewnij się, że MongoDB działa i masz poprawny connection string.
  • 2) Uruchom serwer
    W server/: zainstaluj zależności, utwórz plik .env z URI i JWT_SECRET, a następnie uruchom node index.js (lub npx nodemon index.js dla auto-reload). Serwer nasłuchuje na porcie 5000.
  • 3) Uruchom klienta
    W client/: uruchom npm run dev. Vite startuje na porcie 5173.
  • 4) Otwórz aplikację
    Wejdź na http://localhost:5173.

Konta (Gość vs zarejestrowany)

Autoryzacja jest oparta o ciasteczka. Endpointy signup/login/guest ustawiają ciasteczko auth (JWT). Klient sprawdza bieżącą sesję przez GET /api/account/auth.

  • Gość: tworzy rekord Guest i ustawia krótką sesję (ok. 24h).
  • Zarejestrowany: tworzy rekord User i ustawia dłuższą sesję (ok. 7 dni).

Architektura frontendu

Punkty wejścia klienta

Aplikacja React jest bootstrappowana w client/src/main.jsx, a routing znajduje się w client/src/App.jsx. Kluczowe trasy to lobby (/), ekran wejścia/logowania (/hello), pokoje (/room/:token) oraz dokumentacja (/documentation).

Wywołania REST

UI korzysta z wywołań fetch do endpointów /api. W dev są one proxy’owane przez Vite. Walidacja sesji używa credentials: "include", aby wysłać ciasteczko JWT.

Aktualizacje w czasie rzeczywistym (Socket.IO)

Klient tworzy pojedynczą instancję Socket.IO w client/src/socket.js z autoConnect: false. Poszczególne ekrany łączą się w razie potrzeby i subskrybują zdarzenia dla stanu pokoju, draftu i walki.

Serwer i logika gry

Architektura serwera

Backend uruchamiany jest z server/index.js. Montuje trasy REST pod /api oraz podłącza Socket.IO (server/src/websocket/io.js) do tego samego serwera HTTP. Stan gry jest przechowywany w MongoDB w dokumencie Game.

HTTP API (REST)

Trasy gry są zdefiniowane w server/src/routes/GameRoutes.js, a trasy kont w server/src/routes/AccountRoutes.js.

  • POST /api/play — utworzenie/znalezienie pokoju (quickplay lub play)
  • POST /api/room oraz GET /api/room/:url — tworzenie/wyszukiwanie pokoju
  • GET /api/abilities — lista umiejętności (filtrowana po roli)
  • POST /api/buyAbility — zakup/odblokowanie umiejętności
  • GET /api/endData — dane do ekranu końcowego
  • POST /api/account/signup, /login, /guest, /logout
  • GET /api/account/auth — walidacja sesji (wymaga ciasteczka auth)
  • POST /api/account/abilities — pobranie posiadanych umiejętności

WebSockets (Pokój → Draft → Walka)

Serwer Socket.IO jest zaimplementowany w server/src/websocket/io.js. Główny przepływ wygląda tak:

  • join-room → serwer przypisuje rolę (attacker/defender) i roomId
  • room-state + room-ready → broadcast stanu pokoju i gotowości
  • draft-* → synchronizacja wyborów i ukończenia draftu
  • battle-* → pobieranie i aktualizacja kanonicznego stanu walki
  • leave-room / disconnect → zwolnienie slotu gracza i powiadomienie przeciwnika

Rozwiązywanie umiejętności

Umiejętności są przechowywane jako metadane w kolekcji Ability i kopiowane do dokumentu Game jako talia do walki (z dodatkowym polem currentCooldown).

Gdy klient wysyła battle-use, serwer waliduje turę i cooldown, stosuje efekt, aktualizuje log, przesuwa turę, zdejmuje cooldowny i emituje nowy battle-state.

  • damage — odejmuje HP przeciwnikowi (defender: integrity, attacker: persistence)
  • heal — przywraca HP; szczegóły w sekcji „Nadpisanie leczenia”
  • freeze — zwiększa skipTurns przeciwnika

Nadpisanie leczenia

Serwer implementuje zachowanie „overflow” zależnie od roli, gdy leczenie miałoby przekroczyć 20 HP:

  • Attacker: nadmiar leczenia jest zamieniany na statystykę overflow (zmniejszoną o połowę), która jest dodawana jako bonus do kolejnej umiejętności zadającej obrażenia.
  • Defender: nadmiar leczenia pozwala tymczasowo przekroczyć 20 HP (również zmniejszone o połowę).

Trwałość danych i nagrody

Konta graczy są przechowywane w MongoDB jako User (zarejestrowany) lub Guest (gość). Po zakończeniu meczu serwer przyznaje XP i punkty umiejętności oraz aktualizuje pola level i levelPoints.
